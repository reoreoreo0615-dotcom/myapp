## PHP

### オブジェクト指向 — クラス

| | |
|---|---|
| **内容** | ビジネスロジックをコントローラに書かず責務ごとにクラスへ切り出した。漸進的過負荷の計算、DBアクセス、認可、バリデーション。特に計算ロジックはEloquentに依存させず、値を引数で受け取る純粋なクラスとして書いた。 |

### オブジェクト指向 — 継承

| | |
|---|---|
| **内容** | 漸進法(重量の上げ方)の3クラスに重複していた「前回のトップセットを取り出し、履歴が無ければ目標を出さない」処理を、抽象クラスに集約した。共通の手順は基底クラスの final メソッドに一度だけ実装し、各サブクラスは「トップセットから目標をどう計算するか」だけを実装する構造にした(Template Method パターン)。既存のテストを1行も変えずに全件通ることを確認し、振る舞いが変わっていないことを担保した。 |
| **所感** | 継承はコードを使い回す仕組みだと思っていたが、実際には共通の手順を1箇所に集める仕組みだと分かった。<br>3つのクラスに同じ「履歴が無ければ何もしない」処理が書かれていたのを抽象クラスにまとめたことで、サブクラスは計算部分だけを書けばよくなった。<br>手順を final にしてサブクラスに変えさせないことで、新しい漸進法を追加しても共通の前提が崩れない。<br>インターフェース(ポリモーフィズム)と抽象クラス(継承)の役割の違いも整理できた。 |
| **参考** | app/app/Services/Progression/AbstractProgressionStrategy.php<br>PHPマニュアル: <https://www.php.net/manual/ja/language.oop5.inheritance.php><br>PHPマニュアル: <https://www.php.net/manual/ja/language.oop5.abstract.php> |

### オブジェクト指向 — ポリモーフィズム

| | |
|---|---|
| **内容** | トレーニングの重量の上げ方(漸進法)を差し替え可能にした。インターフェースを定義し3方式を実装。呼び出し側はFactoryからインターフェースを受け取るだけで、どの実装が返るかを知らない。分岐はFactoryの1箇所だけに閉じている。 |
| **所感** | 一番理解が浅かった概念。書籍では「同じメソッド名で違う動きをする」と説明されるが、それだけでは何が嬉しいのか分からなかった。<br>実装して、価値は呼び出し側が実装を知らなくて済むことだと分かった。<br>分岐を呼び出し側に書いていたら方式を追加するたび全部直すことになる。<br>Factoryに閉じたので新しい方式を足しても既存クラスは1行も変えなくていい。<br>開放閉鎖の原則を実感できた。 |
| **参考** | app/app/Services/Progression/<br><https://github.com/reoreoreo0615-dotcom/myapp/blob/main/.claude/docs/screenshots/sp-record.png>(画面に戦略名が表示される)<br>PHPマニュアル: <https://www.php.net/manual/ja/language.oop5.interfaces.php> |

### セッション管理

| | |
|---|---|
| **内容** | Laravelの認証がセッションをどう扱っているかを調査。保存先、有効期限、CookieのHttpOnly/SameSite属性を実際のレスポンスヘッダで確認。ログイン時にセッションIDが再発行されるかを、DBのテーブルをログイン前後で直接比較して検証した。 |
| **所感** | 「ログインすればセッションができる」程度の理解だった。<br>調べて知ったのはログイン時に古いセッションIDを破棄して新しく発行していること。<br>セッション固定攻撃への対策で、フレームワークが黙ってやってくれていた。 |
| **参考** | .claude/docs/security.md §3<br>PHPマニュアル: <https://www.php.net/manual/ja/book.session.php> |

### セキュリティ — CSRF

| | |
|---|---|
| **内容** | トークンがどこで生成されフロントに渡るか、どのミドルウェアが検証しているかを追った。実際にトークン無しのPOSTを投げて419が返ることを確認。さらにLaravel 13では従来方式に加えSec-Fetch-Siteヘッダを見る新しい判定が入っていることをフレームワークのソースから発見し、動作を確かめた。 |
| **所感** | 「CSRFトークンを付ければ安全」で止まっていた。<br>実際に自分で419を出してみると何が検証されて弾かれたのかが具体的に見える。<br>新しい判定方式は書籍にも載っておらず、フレームワークのソースを直接読まないと分からなかった。<br>公式ドキュメントの外側を見にいく必要がある場面があると実感した。 |
| **参考** | .claude/docs/security.md §1<br>PHPマニュアル: <https://www.php.net/manual/ja/security.php> |

### セキュリティ — XSS

| | |
|---|---|
| **内容** | エスケープされる書き方とされない書き方の違いを整理。自分のコードに危険な使い方が無いかgrepし、いずれも0件を確認。さらに種目名にスクリプトタグを実際に登録し、生のHTMLでエスケープされていることを確かめた。 |
| **所感** | エスケープはフレームワークが自動でやると聞いていたが、自動でやらない書き方が用意されていることが盲点だった。<br>便利だからと使った瞬間に穴が開く。<br>自分のコードをgrepして0件だと確認できたのは、知識ではなく事実として安心できた。 |
| **参考** | .claude/docs/security.md §2<br>PHPマニュアル: <https://www.php.net/manual/ja/security.php> |

### セキュリティ — SQLインジェクション

| | |
|---|---|
| **内容** | ORMがプリペアドステートメントでどう防いでいるかを確認。危険なメソッドをgrepし0件を確認。パフォーマンスのため生SQLで書いた集計処理は全行を読み、ユーザー入力がすべてバインディング経由であることを確認した。攻撃文字列を送って弾かれることも検証した。 |
| **所感** | パフォーマンスのために生SQLを書いた箇所があり、そこが安全かどうかを自分で判断する必要があった。<br>「ORMを使っていれば安全」ではなく、どこで文字列連結しているかを自分で確認しないといけないと分かった。 |
| **参考** | .claude/docs/security.md §4<br>PHPマニュアル: <https://www.php.net/manual/ja/pdo.prepared-statements.php> |

### N+1問題

| | |
|---|---|
| **内容** | 一覧画面で項目ごとに関連データを引くため、素直に書くと項目数だけクエリが飛ぶ。バッチ取得メソッドを作り、項目が1件でも31件でも2クエリで済むようにした。項目数を変えてもクエリ数が増えないことをテストで保証している。 |
| **所感** | 名前は知っていたが自分のコードで実際に起きるのを見たのは初めて。8項目なら16クエリで、動きはするので気づかないまま本番に出せてしまうのが怖い。動くと正しいは別だと分かった。<br>クエリ数をテストで固定しておけば、後から誰かが素直な書き方に戻しても気づける。 |
| **参考** | GitHub Issue #10 |

### 論理削除の落とし穴

| | |
|---|---|
| **内容** | 誤削除から復元できるよう論理削除を導入した。このときORMは削除済みを自動除外するが生のクエリビルダは除外しないことが問題になった。生クエリで書いた12箇所すべてを洗い出し、共通メソッドに集約して除外条件を必ず含めるようにした。 |
| **所感** | 「削除したのに集計から消えない」というバグは原因が非常に分かりにくい。実装した本人でもORMと生クエリで挙動が違うことを意識していないと踏む。便利な機能ほど効かない場所を把握しておく必要があると学んだ。 |
| **参考** | GitHub Issue #23 |
