# 学習記録 — 筋トレ管理アプリ「Overload」の開発を通じて

> スプレッドシート貼り付け用。**学習項目 / 内容 / 所感** の3列。
> 所感は「実際に手を動かして分かったこと」「詰まった点」を自分の言葉で書く欄なので、
> 下記はあくまで素案。実感と違う箇所は書き換えること。

## PHP

### オブジェクト指向 — クラス

| | |
|---|---|
| **内容** | ビジネスロジックをコントローラに書かず、責務ごとにクラスへ切り出した。`ProgressionService`(漸進的過負荷の計算)、`WorkoutSetRepository`(DBアクセス)、`WorkoutPolicy`(認可)、`FormRequest`(バリデーション)など。特に `ProgressionService` は Eloquent に依存させず、値を引数で受け取る純粋なロジックとして書いた。 |
| **所感** | 最初はコントローラに全部書けば動くと思っていたが、**テストを書こうとした時点で無理だと分かった**。DBに依存していると、計算ロジックを1つ検証するだけでユーザーとワークアウトとセットを毎回作る必要がある。値を引数で受け取る形にしたら、同じロジックのテストが25件書けた。「責務を分ける」の意味が、理屈ではなく手を動かして腑に落ちた。 |

### オブジェクト指向 — 継承

| | |
|---|---|
| **内容** | フレームワークの基底クラス(`Controller` / `FormRequest` / `Model`)の継承に加え、自分でも基底クラスを設計した。通知処理では `RestNotifier` を基底に `SoundNotifier` / `VibrationNotifier` / `VisualNotifier` を継承させ、「非対応なら何もしない」「例外を投げない」という共通の振る舞いを基底クラスに一度だけ実装した。 |
| **所感** | 継承を「コードを使い回す仕組み」だと思っていたが、実際に設計してみると**共通の振る舞いを1箇所に集める仕組み**だと分かった。基底クラスに例外処理を書いておけば、サブクラスは「この環境で使えるか」と「実際に何をするか」の差分だけ書けばいい。サブクラスを追加するたびに try/catch を書き写す必要がなくなった。 |

### オブジェクト指向 — ポリモーフィズム

| | |
|---|---|
| **内容** | トレーニングの漸進法(重量の上げ方)を差し替え可能にした。`ProgressionStrategy` インターフェースを定義し、ダブルプログレッション / リニア / 5×5 の3つを実装。呼び出し側は Factory からインターフェースを受け取るだけで、どの実装が返ってくるかを知らない。**分岐(`match`)は Factory の1箇所だけ**に閉じている。 |
| **所感** | 一番理解が浅かった概念。書籍では「同じメソッド名で違う動きをする」と説明されるが、それだけでは**何が嬉しいのか**が分からなかった。実際に書いてみて、価値は「呼び出し側が実装を知らなくて済むこと」だと分かった。もし `if ($strategy === 'linear')` を呼び出し側に書いていたら、戦略を追加するたびに全部の呼び出し箇所を直すことになる。Factory に閉じたので、**新しい漸進法を足しても既存クラスは1行も変えなくていい**。これが開放閉鎖の原則の実感だった。 |

### セッション管理

| | |
|---|---|
| **内容** | Laravel の認証がセッションをどう扱っているかを調査した。セッションドライバの保存先、`SESSION_LIFETIME` の意味、Cookie の `HttpOnly` / `SameSite` 属性を実際のレスポンスヘッダで確認。**ログイン時にセッションIDが再発行されるか**を、`sessions` テーブルをログイン前後で直接比較して検証した。 |
| **所感** | 「ログインすればセッションができる」程度の理解だった。調べて驚いたのは、**ログイン時に古いセッションIDを破棄して新しく発行している**こと。これはセッション固定攻撃(攻撃者が用意したIDでログインさせる手口)への対策で、フレームワークが黙ってやってくれていた。`SessionGuard::login()` の内部と、コントローラ側の明示的な `regenerate()` の二重構造になっていることまでソースで確認できた。**知らないうちに守られていたことを、自分で説明できるようになった**のが一番の収穫。 |

### セキュリティ対策 — CSRF

| | |
|---|---|
| **内容** | トークンがどこで生成されフロントに渡るか、どのミドルウェアが検証しているかを追った。実際に `curl` でトークン無しの POST を投げ、**419 が返る**ことを確認。さらに Laravel 13 では従来のトークン方式に加え、`Sec-Fetch-Site` ヘッダを見る Fetch Metadata 判定(`PreventRequestForgery::hasValidOrigin()`)が入っていることを vendor のソースから発見し、`same-origin` で通過・`cross-site` で 419 になることを実際に確かめた。 |
| **所感** | 「CSRFトークンを付ければ安全」で止まっていた。実際に自分で 419 を出してみると、**何が検証されて弾かれたのか**が具体的に見える。Laravel 13 の Fetch Metadata 判定は書籍にも載っていない新しい仕組みで、これはフレームワークのソースを直接読まないと分からなかった。**公式ドキュメントの外側を見にいく必要がある場面がある**と実感した。 |

### セキュリティ対策 — XSS

| | |
|---|---|
| **内容** | Blade の `{{ }}` と `{!! !!}` の違い、Vue の `{{ }}` と `v-html` の違いを整理。自分のコードに危険な使い方が無いか実際に grep し、`v-html` **0件** / `{!! !!}` **0件**を確認した。さらに種目名に `<script>alert(1)</script>` を実際に登録し、生の HTML でエスケープされていることを確かめた。 |
| **所感** | エスケープは「フレームワークが自動でやる」と聞いていたが、**自動でやらない書き方が用意されている**(`{!! !!}` や `v-html`)ことが盲点だった。便利だからと使った瞬間に穴が開く。自分のコードを grep して0件だと確認できたのは、知識ではなく事実として安心できた。 |

### セキュリティ対策 — SQLインジェクション

| | |
|---|---|
| **内容** | Eloquent とクエリビルダがプリペアドステートメントでどう防いでいるかを確認。自分のコードで `DB::raw()` を grep(**0件**)、`selectRaw` を使っている箇所は全行を読み、ユーザー入力がすべて `?` バインディング経由であることを確認した。CSV エクスポートの日付パラメータに攻撃文字列を送り、422 で弾かれることも検証した。 |
| **所感** | パフォーマンスのために生 SQL を書いた箇所(ウィンドウ関数を使った集計)があり、**そこが安全かどうかを自分で判断する必要があった**。「ORMを使っていれば安全」ではなく、「どこで文字列連結しているか」を自分で確認しないといけないと分かった。 |

## JavaScript

### オブジェクト指向 — クラス・継承・ポリモーフィズム

| | |
|---|---|
| **内容** | インターバルタイマーの通知手段(音・バイブレーション・画面フラッシュ)を `class` と `extends` でクラス階層にした。`CompositeNotifier` が複数の通知手段を束ねるが、**個々の型を知らずに `isSupported()` と `notify()` だけを呼ぶ**構造にした。テストでは、継承していない `{ isSupported, notify }` だけのオブジェクトを渡しても動くことを検証した。 |
| **所感** | JavaScript のクラスは PHP と書き方が似ているが、**継承していないオブジェクトでも同じように扱える**(ダックタイピング)のが違いだった。PHP なら型宣言で弾かれるところが JS では通る。これは柔軟だが、逆に「インターフェースを実装し忘れても実行時まで分からない」という怖さもある。テストで担保するしかないと理解した。 |

### 非同期処理とタイマー

| | |
|---|---|
| **内容** | セット間の休憩を計るタイマーを実装。経過時間を `setInterval` のカウント加算ではなく、**開始時刻(`Date.now()`)との差分**で毎回計算する方式にした。加えて `localStorage` に開始時刻を保存し、画面を離れて戻っても正しく復元されるようにした。 |
| **所感** | 最初はカウント加算で作ろうとしたが、**ブラウザはバックグラウンドタブの `setInterval` を間引く**と知って設計を変えた。ジムで別アプリを開いて戻ってきたときに時間が狂う、という実際に起きる問題。テストでは時計を20分先に飛ばして表示が正しいことを検証し、さらに**わざとカウント加算方式に書き換えてテストが落ちることを確認**した。テストが本当に機能するかは、壊してみないと分からないと学んだ。 |

### テスト(Vitest)

| | |
|---|---|
| **内容** | Vitest と Vue Test Utils を導入し、コンポーネントのロジックに36件のテストを書いた(最終的に70件)。フェイクタイマーで長押しの連続増減を検証したり、`localStorage` が使えない環境をモックして壊れないことを確認したりした。 |
| **所感** | それまでテストは PHP 側だけで、フロントは手で触って確認していた。**手で触って気づけるのは「見て分かるバグ」だけ**だと分かった。タイマーの差分計算や `localStorage` の復元は、正常に見えても内部で壊れている可能性がある。テストを書いて初めて、そこに手を入れる自信が持てるようになった。 |

## 設計・開発プロセス

### データベース設計

| | |
|---|---|
| **内容** | 6テーブル(ユーザー / 種目 / メニュー / メニュー種目 / ワークアウト / セット)を設計。外部キーの削除ルール(CASCADE / RESTRICT / SET NULL)を用途ごとに使い分け、インデックスを実際のクエリに合わせて張った。 |
| **所感** | 外部キーの削除ルールで**実際にデータ漏洩バグを作ってしまった**のが一番の学び。ユーザーの独自種目に `SET NULL` を設定していたため、ユーザーを削除するとその種目が「全員に見える既定種目」に昇格する状態になっていた。設計時は「参照が壊れないように」としか考えていなかったが、**NULL が業務上どういう意味を持つか**まで考える必要があった。 |

### N+1 問題

| | |
|---|---|
| **内容** | 記録画面は種目ごとに「前回の記録」を引くため、素直に書くと種目数だけクエリが飛ぶ。バッチ取得メソッドを作り、**種目が1件でも31件でも2クエリ**で済むようにした。種目数を変えてもクエリ数が増えないことをテストで保証している。 |
| **所感** | 名前は知っていたが、自分のコードで実際に起きるのを見たのは初めて。8種目なら16クエリで、動きはするので**気づかないまま本番に出せてしまう**のが怖い。「動く」と「正しい」は別だと分かった。クエリ数をテストで固定しておけば、後から誰かが素直な書き方に戻しても気づける。 |

### 論理削除の落とし穴

| | |
|---|---|
| **内容** | 誤削除から復元できるよう論理削除(SoftDeletes)を導入した。このとき、**Eloquent は削除済みを自動で除外するが、生のクエリビルダ(`DB::table()`)は除外しない**ことが問題になった。パフォーマンスのために生クエリで書いた12箇所すべてを洗い出し、共通メソッドに集約して除外条件を必ず含めるようにした。 |
| **所感** | 「削除したのに集計から消えない」というバグは、原因が非常に分かりにくい。実装した本人でも、Eloquent と生クエリで挙動が違うことを意識していないと踏む。**便利な機能ほど、効かない場所を把握しておく必要がある**と学んだ。 |

### AIツール(Claude Code)を使った開発

| | |
|---|---|
| **内容** | 設計・仕様の確定・レビューを自分が担い、確定した仕様の実装を AI エージェントに委譲する体制を作った。プロジェクト固有の規約(集計時の除外条件、開発DBを壊さない、N+1を放置しない等)をファイルに明文化し、エージェントに読ませてから作業させた。 |
| **所感** | **AIの出力をそのまま受け入れないことが最も重要**だと分かった。実際、ユーザー削除時のデータ漏洩、論理削除導入時の副作用、設定が黙ってリセットされるバグなどを、レビューで見つけて修正させた。一方で、AI 側から「仕様のここが矛盾している」「この判定基準は頻度で意味が変わる」と指摘されたこともあり、**自分の仕様の雑さに気づかされた**。規約に矛盾があるとエージェントは都合の良い方を選ぶので、指示を書く側の精度が問われる。人に作業を依頼するときと同じで、**曖昧な指示は曖昧な成果物になる**という当たり前のことを、繰り返し実感した。 |

## 全体を通して

| | |
|---|---|
| **内容** | Laravel 13 + Inertia + Vue 3 で筋トレ管理アプリを設計から実装まで行った。Issue 29件、テスト443件(PHP 373 / JS 70)、CI をグリーンに保ちながら開発した。 |
| **所感** | 目標に「理解している状態から人に説明できる状態へ」と書いたが、**説明しようとして初めて分からないことに気づく**場面が何度もあった。特にセキュリティは「フレームワークが守ってくれる」で止まっていて、何をどう守っているかは説明できなかった。実際に攻撃文字列を投げて 419 が返るのを見て、ソースを追ってどのクラスが弾いているかを特定して、ようやく人に話せる形になった。<br><br>もう一つの収穫は、**対策できていないことを正直に書けるようになった**こと。調査の結果、CSPヘッダを送っていない、新規登録にレート制限が無いなど7項目が未対策だと分かり、それも文書に残した。以前なら「できていない」と書くのを避けていたと思うが、**現状を正確に把握していることの方が価値がある**と考えられるようになった。 |
