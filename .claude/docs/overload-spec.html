Overload

筋トレ管理アプリ / 設計仕様

記録するだけのアプリは既にたくさんある。Overload は「今日は何kgを何回やればいいか」を先に言う。筋肥大の唯一の原則である漸進的過負荷を、アプリ側が計算して提示する。

01 / Positioning

既存アプリは「記録帳」で止まっている

Strong、Hevy、FitNote — トレーニング記録アプリは飽和している。だがそのほとんどは入力した数字を保管して並べ直すだけで、次のセッションで何をすべきかは利用者の頭の中に委ねられている。

筋力・筋量が伸びる条件は一つしかない。前回よりわずかに強い刺激を与え続けること — 漸進的過負荷(progressive overload)である。にもかかわらず、その計算をアプリが肩代わりしてくれない。ジムのベンチに寝転がりながら「先週は何キロで何回上がったっけ」とスクロールして探し、暗算する。この数十秒が、記録を続けられない理由になっている。

Overload が引き受ける2つのこと

① 種目を開いた瞬間に今日の目標が数値で出ていること。② 入力欄にその数値が最初から入っているので、上がったらタップ1回で確定できること。

02 / Core Logic

ダブルプログレッションで次の目標を決める

重量とレップ数の2軸を交互に伸ばす、ウェイトトレーニングで最も広く使われている漸進法。実装はごく単純な分岐で済み、しかも純粋関数なのでユニットテストを厚く書ける。

種目目標レンジ刻み前回の結果提示する今日の目標
ベンチプレス8 – 122.50 kg60.0 kg × 1262.5 kg × 8  ↑重量
ベンチプレス8 – 122.50 kg60.0 kg × 960.0 kg × 10  ↑レップ
ダンベルカール10 – 152.00 kg14.0 kg × 1516.0 kg × 10  ↑重量
レッグプレス10 – 155.00 kg180.0 kg × 13180.0 kg × 14  ↑レップ

刻み幅(increment)を種目ごとに持つ理由

「一律 +2.5kg」では現実に合わない。バーベルは 1.25kg プレートを左右に足して +2.5kg が最小、ダンベルは 1kg 刻みのラックなら +2kg、マシンのピンは 5kg 刻みが多い。器具の物理的制約がそのまま刻み幅になるので、これは種目マスタの属性として持つのが正しい。

03 / Data Model

セッション・セット・種目の3層構造

「1回のジム」を workouts、「そのなかの1セット」を workout_sets、「ベンチプレスという種目そのもの」を exercises に分ける。ここを混ぜると集計クエリが破綻する。

exercises — 種目マスタ

カラム型役割
user_idbigint nullablenull なら既定種目(シーダー投入)、値があればユーザー独自種目
namestringベンチプレス
muscle_groupenumchest / back / shoulders / legs / arms / core
movement_typeenumpush / pull / legs / core — Phase 2 の部位バランス可視化用。今は使わないが列だけ先に置く
equipmentenumbarbell / dumbbell / machine / cable / bodyweight
is_bodyweightboolean自重種目フラグ。true のとき weight は「加重分」を意味する
weight_incrementdecimal(4,2)漸進の刻み幅。barbell 2.50 / dumbbell 2.00 / machine 5.00
target_rep_mintinyint目標レップ下限(既定 8)
target_rep_maxtinyint目標レップ上限(既定 12)

workout_sets — 実測値

カラム型役割
workout_idbigint所属セッション
exercise_idbigint種目
set_numbertinyintそのセッション内でのセット順
weightdecimal(5,2)999.99kg まで。0.25kg 刻みも表現できる
repssmallint挙上回数
rpedecimal(3,1) null主観的運動強度 6.0〜10.0。Phase 2 のナビ補正の伏線
is_warmupbooleanこれが無いと数字が全部狂う。アップのセットを総ボリューム・記録更新・ナビ計算から除外する

設計の先送りを許さない2点。movement_type と rpe は MVP では一切使わないが、列は最初から用意する。データが数百件積まれた後のカラム追加とバックフィルは、今なら10秒で済む作業を数時間に変える。

インデックス

テーブルインデックス効かせたいクエリ
workouts(user_id, performed_on)カレンダー表示・期間集計
workout_sets(exercise_id, workout_id)「この種目の前回の記録」 — ナビが毎回叩く最重要クエリ

記録画面は種目ごとに前回値を引くため、素直に書くと Exercise の数だけクエリが飛ぶ。N+1 が必ず出る場所なので、Eager Loading とサブクエリでの解決を実装課題として明示的に扱う。

05 / Scope

MVP に入れるもの、入れないもの

Inertia + Vue を選んだぶん学習量が増えるので、機能側は絞る。「記録できて、次の目標が出て、伸びが見える」まででいったん完成とする。

MVP に入れる

  • 認証(公式スターターキット)
  • 種目マスタ + シーダーで主要30種目
  • ユーザー独自種目の追加
  • ルーティン(メニュー)の作成・編集
  • ワークアウト記録 — 前回値プリセット / タップ1回で確定
  • 漸進的過負荷ナビ(ProgressionService)
  • 種目別履歴 + 推定1RM推移グラフ
  • ダッシュボード(ボリューム・連続記録・PR)

Phase 2 以降に回す

  • 停滞(プラトー)検知とデロード提案
  • 部位バランス可視化(push / pull 比率)
  • RPE によるナビ補正
  • 体重・体脂肪率の記録
  • PWA / オフライン記録
  • 記録の公開・共有
  • インターバルタイマー通知

06 / Workflow

Opus が設計し、Sonnet が実装する

設計判断・スキーマ・Issue 分解・レビューは Opus が持つ。マイグレーション、モデル、コントローラ、Vue コンポーネント、テストといった仕様が確定した後の写経的な作業をサブエージェントに委譲する。

委譲するサブエージェント(予定)

エージェント担当渡す情報
laravel-backendマイグレーション / モデル / リレーション / コントローラ / FormRequest確定したスキーマ定義と受入条件
vue-frontendInertia ページ / Vue コンポーネント / Tailwind スタイル画面モックと props の型
test-writerFeature テスト / ProgressionService のユニットテスト期待する入出力の表

定義ファイルは .claude/agents/ に置く。モデルは Sonnet を指定し、各エージェントに Laravel 13 の規約・Pint の整形ルール・このドキュメントの設計方針を読ませた状態で起動する。

07 / Issues

GitHub Issue への落とし込み

既存の汎用 Issue #2〜#4 を筋トレアプリの仕様で具体化し、不足分を追加する。依存の順に並べてあり、上から順に着手できる。

Issue内容担当段階
#3 DB設計・マイグレーション作成 — 6テーブル + インデックス Sonnet 基盤
#2 認証機能 — 公式スターターキット導入(Inertia + Vue 3) Sonnet 基盤
#6 Laravel Pint 導入 — 整形ルール確定 Sonnet 基盤
#5 CI(GitHub Actions) — Pint チェック + テスト実行 Sonnet 基盤
#7 種目マスタのシーダー — 主要30種目に increment とレップレンジを設定 Opus 中核
#8 ProgressionService — ダブルプログレッション + 推定1RM、ユニットテスト付き Opus 中核
#9 ルーティン(メニュー)管理 — CRUD と種目の並び替え Sonnet 機能
#10 ワークアウト記録画面 — 前回値プリセット / タップ1回確定 / N+1 対策 Sonnet 機能
#11 種目別履歴 — 推定1RM推移グラフと全セット一覧 Sonnet 機能
#4 ダッシュボード・共通レイアウト — ボリューム / 連続記録 / 直近PR Sonnet 機能
#12 サブエージェント構成の整備 — .claude/agents/ 定義 Opus 体制

着手順の理由。スキーマ(#3)が固まらないと他が全部書き直しになるので最優先。Pint と CI を機能実装より前に入れるのは、後から一括整形すると差分が巨大になりレビュー不能になるため。ProgressionService はアプリの価値そのものなので、画面より先にロジックとテストを固める。
