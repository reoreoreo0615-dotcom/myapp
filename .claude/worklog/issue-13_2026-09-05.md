## 修正したバグ(最重要)

### 症状

```
exercises.user_id → users    DELETE_RULE: SET NULL   ← 修正前
```

ユーザーを削除すると、そのユーザーの独自種目の `user_id` が `NULL` になる。
このアプリでは **`user_id = NULL` は「全ユーザーに見える既定種目」を意味する**ため、
削除したユーザーの private な種目が全員に公開されていた。

管理者によるユーザー削除だけでなく、**Breeze が既に実装していた
プロフィール画面の「アカウント削除」でも発生する**状態だった。

### 対処(2段構え)

**1. 外部キーを CASCADE に変更**

「ユーザーの独自種目はそのユーザーに属する」が正しいセマンティクス。

**2. `DeleteUserService` でトランザクション + 明示的な順序で削除**

FK のカスケードだけに頼らない。理由は2つ:

- **MySQL は `users` から出る複数のカスケード経路の実行順序を保証しない**
- `workout_sets.exercise_id` が **RESTRICT** のため、セット記録を先に消さないと
  種目を削除できない

```php
DB::transaction(function () use ($user) {
    $user->workouts()->delete();   // → workout_sets が CASCADE で消える
    $user->routines()->delete();   // → routine_exercises が CASCADE で消える
    $user->exercises()->delete();  // ← ここで初めて RESTRICT に引っかからない
    $user->delete();
});
```

`ProfileController@destroy`(自己削除)もこのサービス経由に変更した。

## 設計上の判断

### 1. `role` enum ではなく `is_admin` boolean

現時点で必要な区分は「管理者かどうか」の2値のみ。enum にすると値追加のたびに
マイグレーションが必要になる割に得るものがない。3つ目のロールが必要になった時点で移行する。

### 2. 管理者の任命は artisan コマンド

`php artisan user:make-admin {email}`。マイグレーションにメールアドレスを埋め込むと、
他環境で無意味なデータが入るため。存在しないメールでは exit code 1 とメッセージを返し、
例外を投げっぱなしにしない。

### 3. 締め出し防止のガード

- 自分自身は削除できない
- 最後の管理者からは管理者フラグを剥奪できない

### 4. 一覧はテーブルではなくカード型リスト

375px 幅での横スクロールを避けるため。

## 発生した事故(2件・いずれも復旧済み)

### 1. エージェントが開発DBを破壊した

FK の確認過程で、開発用DB `myapp` に対して `migrate:fresh` を実行し、
実ユーザーと既定種目31件を消去した。エージェント自身が正直に報告した。

復旧: ユーザーを作り直し、`db:seed` で種目31件を再投入。
**元のパスワードと登録日時は復元不可能。**

**再発防止として `.claude/agents/laravel-backend.md` に
「開発DB `myapp` に対して `migrate:fresh` を実行しない。検証は `myapp_testing` を使う」
を追記した。**

### 2. レビュー時の rollback テストで管理者フラグが消えた

`migrate:rollback --step=2` で `is_admin` 列ごと削除され、`migrate` での再作成時に
`default false` に戻っていた。`user:make-admin` を再実行して復旧。

**破壊的な検証は開発DBではなくテストDBで行うべきだった。** 上記の再発防止に含める。

仕様に明記していなかった記述漏れ。**別Issueで対応する。**
