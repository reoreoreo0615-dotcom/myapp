## 実装内容
`AdminUserController@destroy` に、自己削除ガードとは**独立したルール**として
「削除後に管理者が0人にならないこと」の明示的チェックを追加した。

```php
$wouldLeaveNoAdmins = $user->is_admin
    && User::where('is_admin', true)->count() <= 1;

if ($wouldLeaveNoAdmins) {
    return Redirect::route('admin.users.index')
        ->with('error', '最後の管理者を削除することはできません。');
}
```

既存の flash.error 経路を使用。500 にはならない。

## 変更ファイル
- `app/app/Http/Controllers/Admin/AdminUserController.php`
- `app/tests/Feature/Admin/AdminUserManagementTest.php`(テスト2件追加)

## 設計上の判断

### チェック順を「最後の管理者 → 自己削除」に入れ替えた

`EnsureUserIsAdmin` により destroy を叩けるのは管理者のみ。したがって
「自分以外の管理者が最後の管理者を削除する」HTTP経路は**構造的に発生しない**
(操作者自身も管理者なので、対象が別の管理者なら管理者数は必ず2以上になる)。

つまり「削除対象が最後の管理者」に到達できるのは、実質「自分自身が最後の管理者」の場合のみ。
自己削除チェックを先に置くと新ガードは**デッドコードになり、テストで発火を検証できない**。

順序を入れ替えたことで、最後の管理者による自己削除時に新ガード由来のメッセージが返り、
独立したルールとして機能・検証できるようになった。

## 残課題
「別の管理者が最後の管理者を削除する」経路は現行の認可設計では原理的に到達不能。
今回のガードは**将来の設計変更(自己削除ガードの撤廃、別ルートの追加など)に対する防御**
として機能する。この性質をコード内コメントにも明記した。
