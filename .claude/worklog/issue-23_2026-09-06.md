## 実装内容
「間違えても直せない記録アプリは信頼できない」という最大の弱点を潰した。

### ① 終了済みワークアウトの編集モード
`workouts.editing_started_at`(nullable timestamp)を追加。
`WorkoutPolicy::update()` は「未終了、または `editing_started_at` が非null」で許可。
`finished_at` 自体には触れない。

**`progression_snapshot` は再計算しない。** そのセッション時点で提示した目標の記録であり、
後から書き換えると履歴の意味が壊れるため。`WorkoutProgressionSnapshotService` は無変更。

### ② 過去日での記録
`StoreWorkoutRequest` に `performed_on`(`nullable|date|before_or_equal:today`)。
目標算出は `lastWorkingSetsFor(Many)` に `$onOrBeforeDate` と `$excludeWorkoutId` を追加し、
`workouts.performed_on <= 指定日 AND workouts.id != 自分` で絞る。

### ③ SoftDeletes
`workouts` / `workout_sets` / `routines` に導入。`exercises` と `body_logs` は対象外。
削除成功時に `flash.undo`(復元URL)を積み、「元に戻す」を出す。

## 最重要の落とし穴への対応: `DB::table()` と論理削除

Eloquent と違い `DB::table()` は論理削除を自動で除外しない。
`WorkoutSetRepository` の生クエリ**8箇所すべて**が該当していた。

共通の `activeWorkoutSetsQuery()` を新設し、両テーブルの `deleted_at IS NULL` を必ず含める:

```php
private function activeWorkoutSetsQuery(): Builder
{
    return DB::table('workout_sets')
        ->join('workouts', 'workouts.id', '=', 'workout_sets.workout_id')
        ->whereNull('workout_sets.deleted_at')
        ->whereNull('workouts.deleted_at');
}
```

置き換えた箇所: `lastWorkingSetsFor` / `lastWorkingSetsForMany` /
`historyTopSetsPerWorkout` / `historyAllSets` / `personalBest` / `hasAnyRecordedSets` /
`weeklyVolume` / `trainedWeekStarts` / `monthlyBestComparison` / `latestPersonalBest`(計12箇所)

**セット自身の論理削除と親ワークアウトの論理削除の両方**を除外することを13件のテストで検証。

## エージェントが発見した副作用(指示に無かった。いずれも実害あり)

### 1. メニューを削除するとワークアウト表示がクラッシュする
`Workout::routine()` は既定で trashed を除外するため、参照先メニューが論理削除されると
`$routine->routineExercises()` を null に対して呼んで落ちる。
`->withTrashed()` を付けて解決し、回帰テストを追加。

### 2. `DeleteUserService` が壊れる
`$user->workouts()->delete()` が論理削除(UPDATE)になり、物理FKカスケードが発火しない。
`workout_sets` が残置され、後続の `exercises` の RESTRICT 削除が失敗する。
`withTrashed()->forceDelete()` に変更。ユーザー削除は完全消去が正しいという要件は維持。

### 3. セット0件の自動破棄は復元対象にすべきでない
`finish()` の空ワークアウト破棄は「ユーザーの意図的な削除」ではないため `forceDelete()` に変更。

## 設計上の判断

### 過去日の目標算出は `<=`(同日以前、自分自身は除外)
「その日付より前」を厳密に `<` と解釈すると、同日の別ワークアウト(1日2部練)まで除外され、
既存の「今日」ケースの挙動を壊す。`<=` + 自己除外なら、
今日のケースでは既存挙動と完全に一致し、過去日入力時のみ「その日より後の記録を使わない」を満たす。

### 同日複数ワークアウトは許可しない
`redirectToActiveWorkout()`(未終了は1件まで)は変更しない。
過去日入力は「入力し忘れた日を後から埋める」用途であり、
同時並行ワークアウトを許可する要求ではないと判断。
