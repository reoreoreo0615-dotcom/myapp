## 実装内容

種目マスタのシーダーを作成し、既定種目31件を投入した。
実装は Sonnet サブエージェントに委譲し、Opus がレビュー・修正した。

### 構造

`weight_increment` を器具区分の定数マップから、レップレンジをコンパウンド/アイソレーションの
フラグから**機械的に算出する構造**にした。種目定義には器具と compound フラグだけを書き、
数値を直接書かない。これにより31件分の値がブレることがない。

```php
private const WEIGHT_INCREMENT = [
    'barbell' => 2.50, 'dumbbell' => 2.00, 'machine' => 5.00,
    'cable' => 2.50, 'bodyweight' => 1.25,
];
private const COMPOUND_REPS   = ['min' => 6,  'max' => 10];
private const ISOLATION_REPS  = ['min' => 10, 'max' => 15];
```

冪等性は `Exercise::updateOrCreate(['user_id' => null, 'name' => ...], [...])` で担保。

## レビューで修正した3件

エージェントの実装は指示に忠実だったが、**指示自体が誤っていた箇所**が2件あった。

### 1. リアレイズ: `movement_type` を push → pull

私の指示「肩は push」が粗すぎた。**リアレイズが鍛える後部三角筋は pull 群**であり、
PPL スプリットでも pull の日に入る。push 扱いのままだと Phase 2 の
「押す/引くバランス可視化」が本来の目的(押す種目に偏ると怪我する、を検知する)を
果たせなくなる。後部三角筋は最も偏りが出やすい部位なので、ここを push に数えるのは致命的。

### 2. アップライトロウ: `movement_type` を push → pull

同上。動作としてウェイトを身体側に引く垂直プル。エージェント自身も報告で
「動作ベースで見れば pull の方が自然」と懸念を挙げていた。

### 3. ショルダープレス: `equipment` を machine → barbell

「ダンベルショルダープレス」が別途あるため無印をマシンとみなす判断は理解できるが、
それだと**バーベルのオーバーヘッドプレスが種目マスタから完全に欠落**する。
ビッグ3(ベンチ・スクワット・デッドリフト)に次ぐ主要コンパウンドなので barbell に変更。
マシンのショルダープレスはユーザー独自種目で追加できる。

### 修正後の movement_type 分布

```
push 12 / pull 11 / legs 6 / core 2
```

push と pull がほぼ均衡しており、バランス指標の基準として妥当。

## 残課題

### `exercises.name` に UNIQUE 制約がない(エージェントの指摘)

冪等性は `updateOrCreate` のロジックで担保しているが、DB 制約では守られていない。
ただし **`unique(user_id, name)` を張っても解決しない**点に注意が必要。
MySQL は UNIQUE インデックス内の NULL を互いに異なる値として扱うため、
`user_id = null` の既定種目同士では重複を防げない。

対策が必要になった場合の選択肢:
- 既定種目用に `user_id` の代わりにセンチネル値を使う(設計が汚れる)
- アプリ層のバリデーションで担保する(現実的)
- 生成カラム + UNIQUE で NULL を特定値に畳む

**現時点ではシーダー経由でしか既定種目が作られないため実害はない。**
ユーザー独自種目の追加機能(Issue #9)を実装する際に、
同名種目を許すかどうかの仕様とあわせて再検討する。
