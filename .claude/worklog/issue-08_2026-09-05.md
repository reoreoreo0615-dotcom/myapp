## 実装内容

このアプリの価値そのものである漸進的過負荷ロジックを実装し、テストで固めた。
**実装とテストを別々の Sonnet エージェントに分離**して委譲し、Opus がレビューした。
同一エージェントに両方やらせると、テストを通すために実装を歪めるインセンティブが働くため。

### `app/app/Services/ProgressionService.php`

**Eloquent / DB に一切依存しない純粋ロジック。** 値を引数で受け取り、素の配列・スカラを返す。

| メソッド | 役割 |
| --- | --- |
| `nextTarget()` | ダブルプログレッション。`reps >= rep_max` なら重量 +increment / reps を rep_min にリセット、そうでなければ同重量で reps +1。前回の記録が無ければ null |
| `estimateOneRepMax()` | Epley 式 `1RM = W × (1 + R/30)`。小数第1位まで |
| `pickTopSet()` | 最大重量、同重量なら最大レップのセットを選ぶ。`is_warmup` は必ず除外 |

### `app/app/Repositories/WorkoutSetRepository.php`

DB アクセスを分離。`lastWorkingSetsFor(userId, exerciseId)` は **2クエリ**で、
`user_id` で絞り、`is_warmup = false` のセットを持つ直近ワークアウトのセットを返す。

## 検証結果(Opus が自分で実行)

期待入出力表を PHP スクリプトにして tinker で直接実行し、**17項目すべて一致**を確認した。

```
nextTarget(60,12,2.5,8,12)   → 62.5kg × 8   type=weight   OK
nextTarget(60,9,2.5,8,12)    → 60.0kg × 10  type=reps     OK
nextTarget(0,10,1.25,6,10)   → 1.25kg × 6   type=weight   OK  ← 自重種目の加重開始
1RM(60,1)                    → 60.0                       OK  ← 1レップは重量そのもの
1RM(60,0)                    → InvalidArgumentException   OK
pickTopSet 同重量なら最大レップ → 60×10                    OK  ← 最後のセット(55×12)を選ばない
pickTopSet アップが最重量でも除外 → 60×8                   OK  ← Opus が追加した検証
```

最後のケースは私が独自に追加した。**アップで `100kg × 1` を挙げてから本番 `60kg × 8` をやった場合**、
`is_warmup` の除外が漏れていると 100kg が基準になりナビが完全に壊れる。ここが守られていることを確認した。

テストは `php artisan test` で **35件 / 65アサーション 全パス**。

## 設計上の判断

### 1. ProgressionService から Repository への import を除去した(レビュー修正)

エージェントの実装には docblock の `{@see WorkoutSetRepository}` のためだけに
`use App\Repositories\WorkoutSetRepository;` が入っていた。実害は無いが、
**「DB層に依存しない」というこのクラスの契約を一目で損なう。**
後続の実装者(特に Sonnet エージェント)がファイルを開いたとき、import があると
「使ってよい」と解釈する余地がある。import を消し、docblock に

> このクラスに DB アクセスを追加しないこと。テスタビリティのための境界であり、
> 実データの取得は App\Repositories\WorkoutSetRepository の責務。

と明示的な禁止を書いた。委譲前提の開発では、境界を暗黙にせず文章で守る必要がある。

### 2. テストの接続先を SQLite から MySQL に変更した

`phpunit.xml` は既定で `sqlite` / `:memory:` を使っていた。本番は MySQL 8.0。

**SQLite には真の DECIMAL 型が無く float として扱われる。** enum 制約も unsigned も無視する。
このアプリは `decimal(5,2)` の重量計算が根幹なので、「テストは通るが本番で挙動が違う」
典型パターンのリスクがあった。

実際に MySQL で流したところ35件とも通り、**懸念した乖離は起きていなかった**。
しかしリスク自体は残る(今後スキーマが増えるほど乖離の余地が広がる)ため、接続先を切り替えた。
実測 SQLite 5.3s / MySQL 10.3s と差は小さく、本番同等で検証する価値の方が大きいと判断した。

テスト用に `myapp_testing` データベースを作成し、開発用の `myapp` とは分離している。

### 3. `estimateOneRepMax` は reps = 1 のとき Epley 式を適用しない

Epley 式をそのまま適用すると `60 × (1 + 1/30) = 62.0` となるが、
**1レップ挙がった重量は定義上それ自体が 1RM** なので、weight をそのまま返す。

## 残課題

### `lastWorkingSetsFor` は種目1件ごと → 記録画面(#10)で N+1 になる

現在のシグネチャは `lastWorkingSetsFor(int $userId, int $exerciseId)` で、種目1件につき2クエリ。
**記録画面は5〜8種目を同時に表示するため、素直に呼ぶと 10〜16クエリの N+1 になる。**

#10 の実装時に `lastWorkingSetsForMany(int $userId, array $exerciseIds)` 相当の
バッチ取得メソッドが必須。Issue #10 に追記済み。
