## 背景
全体の動作検証を行った際、履歴画面のグラフが**デスクトップで画面幅の4割程度しか
使っていない**ことをスクリーンショットで発見した。記録が8点あってもグラフが小さく、
推移が読み取りにくい状態だった。

## 原因
`ExerciseHistoryChart.vue` が SVG に `width` 属性を**固定ピクセルで直接指定**しており、
親要素が広くても伸びなかった。

`overflow-x-auto` に入れているのはスマホで潰れないよう最小幅を確保するためで、
その意図自体は正しいが、デスクトップでの拡大が考慮されていなかった。

## 変更ファイル
- `app/resources/js/Components/ExerciseHistoryChart.vue`

## 設計上の判断

### CSS の `width:100%` + `viewBox` 方式を却下した(エージェントの判断)
Issue 本文で私が提案した方式だが、実装担当が理由を挙げて却下し、別案を採った。

- 等比拡大にすると**幅を伸ばすほど高さも比例して伸び**、「縦長すぎる」問題が発生する
  (8点で幅2.2倍 → 高さも500px近くになる)
- `preserveAspectRatio="none"` で高さだけ固定すると、**軸ラベルや点がすべて横に歪む**。
  tabular-nums で桁を揃える計器デザインの意図に反する

**採用した方式**: CSS での拡縮ではなく、`ResizeObserver` で親要素の幅を実測し、
**SVG の座標系(viewBox)自体を描き直す**。

- 高さは常に 224px 固定 → 縦長になりようがない
- ピクセル単位が実寸なので文字・点が一切歪まない

この判断は妥当。私の提案した方式では品質が落ちていた。

### 点が少ないときの間延びを防ぐ上限を設けた
点間隔に `MAX_POINT_GAP = 120px` の上限を置き、
`renderWidth = clamp(containerWidth, chartWidth, maxChartWidth)` とした。

```
n=0,1,2 → 280px のまま(伸びない)
n=3     → 324px(+16%)
n=8     → 1280px幅で924pxまで伸びる
```

「>= 最小幅なら常に親幅いっぱい」という私の指示から意図的に外れた判断だが、
点が2個で画面いっぱいに広がると不自然なので、こちらが正しい。

## レビューで追加修正した点

エージェントが懸念として報告していた項目を修正した。

**「← 横にスクロールできます →」が不要な場面で表示されていた。**
条件が `points.length > 6` という**点数のみの静的判定**だったため、
デスクトップでグラフが収まっていてもヒントが出ていた。

```js
// 実際にはみ出すときだけ出す
const isScrollable = computed(
    () => containerWidth.value > 0 && renderWidth.value > containerWidth.value + 1,
);
```
