設計仕様書で Phase 2 として約束し、`exercises.movement_type` の列まで #3 で仕込んだ機能。
**未実装のままだと、その列を残した判断自体が誤りだったことになる。**

このアプリの差別化軸は「記録帳で止まらず、次に何をすべきかを言う」こと。
停滞検知はその核心。

---

## ① 停滞(プラトー)検知

### 判定ロジック(要確定)
```
対象: is_warmup = false のトップセット
指標: 通常種目は推定1RM、自重種目はレップ数(Issue #17 の決定に従う)

直近 N 回のセッションで指標が更新されていない → 停滞
```

- [ ] **N の決め方を判断すること。** 「3週間」と仕様書に書いたが、
      週1回の種目と週3回の種目で意味が変わる。
      **回数ベース(直近3セッション)と期間ベース(3週間)のどちらが適切か
      検討し、理由を報告すること**
- [ ] 停滞と判定する条件に「更新がない」だけでなく
      「**下がっている**」を区別するか判断すること(体調不良の1回と本当の停滞は違う)

### 提案内容
停滞を検出したら**具体的な次の手**を出す。「停滞しています」だけでは価値がない。

- [ ] **デロード提案**: 「重量を10%落として3セッション、その後元の重量に戻す」
- [ ] **レップレンジ変更の提案**: 現在のレンジで頭打ちなら、
      レンジ自体を下げる(例 8-12 → 5-8)提案
- [ ] 提案は**押し付けない**。「停滞かもしれません」程度の表現にし、
      ユーザーが無視できること(体調やサイクルの都合がある)

### 表示場所
- [ ] ダッシュボードに「停滞している種目」を出す
- [ ] 記録画面で該当種目を開いたときにも出す
- [ ] **記録操作を邪魔しないこと。** 差別化軸は入力速度

## ② 部位バランスの可視化

`exercises.movement_type`(push / pull / legs / core)を使う。

### なぜ必要か
**押す種目に偏ると肩を痛める。** 特にベンチプレス中心の人は
push が過多になり、pull が不足しがち。数字で見えないと気づけない。

### 仕様
- [ ] 期間内(直近4週など)の**セット数**または**総挙上重量**を
      `movement_type` 別に集計する。**どちらを指標にするか判断し理由を報告すること**
      (セット数は種目間で公平、総挙上重量は脚が過大になる)
- [ ] push / pull の比率を出す。**理想は概ね 1:1**
- [ ] 偏りが大きい場合に警告する。**閾値を判断すること**
- [ ] `is_warmup = false` で絞ること
- [ ] 記録が少ない期間は判定しない(数セットで比率を語らない)

### 表示
- [ ] ダッシュボードまたは履歴画面に配置
- [ ] 棒グラフか比率バー。既存の `ExerciseHistoryChart.vue` の作りに合わせるか、
      シンプルな比率バーを新規に作るか判断すること

## 受入条件
- [ ] 停滞している種目が検出され、具体的な提案が出る
- [ ] 判定ロジック(N の値、下降の扱い)の根拠が報告されている
- [ ] 自重種目はレップ数で判定される(#17 の決定に従う)
- [ ] push / pull の比率が出て、偏りが警告される
- [ ] 集計が `is_warmup = false` で絞られている
- [ ] 記録が少ない期間で誤判定しない
- [ ] 記録操作の手数が増えていない
- [ ] 既存テストが通る
