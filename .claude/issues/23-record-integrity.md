**「間違えても直せない記録アプリ」は信頼できない。** これが現状いちばんの弱点。

## 現状の問題(調査済み)

| 問題 | 実際に起きること |
| --- | --- |
| 終了したワークアウトを修正できない | `WorkoutPolicy::update` が `finished_at === null` を要求。セットの数値を打ち間違えて終了したら**永久に間違ったまま** |
| 過去の記録を後から入力できない | `performed_on` は今日固定。ジムで入力し忘れたら**その日のトレーニングは記録できない** |
| 削除が物理削除 | `SoftDeletes` 未使用。誤って消したメニュー・ワークアウトは**復元不可** |

毎回の入力に緊張感が生まれ、使うのが億劫になる。記録アプリとして致命的。

---

## ① 終了済みワークアウトの編集

### 方針
`WorkoutPolicy::update` の「終了済みは編集不可」を撤回するのではなく、
**明示的な「編集モード」に入る操作を挟む。**

- [ ] 終了済みワークアウトの画面に「記録を修正する」ボタン
- [ ] 押すと編集モードになり、セットの追加・編集・削除ができる
- [ ] 編集モード中は「修正中」と分かる表示にする
- [ ] 「修正を終える」で閲覧専用に戻る

### 注意: progression_snapshot を再計算しないこと
Issue #10 で凍結した `workouts.progression_snapshot` は
**そのセッション時点の「前回」と「今日の目標」の記録**。
後から修正しても**当時の目標は変わらない**。再計算すると履歴の意味が壊れる。

## ② 過去の日付での記録

- [ ] ワークアウト開始時に日付を選べるようにする(既定は今日)
- [ ] **未来日は不可**(`before_or_equal:today`)
- [ ] 過去日で始めた場合、`progression_snapshot` は
      **その日付より前の記録**から算出すること。今日時点の記録から計算しない
- [ ] 同じ日に複数のワークアウトを許すか判断すること
      (現状 `redirectToActiveWorkout()` は未終了が1件だけの前提)

## ③ 誤削除からの復元(SoftDeletes)

対象を絞る。**全テーブルに入れると FK とユニーク制約が複雑になる。**

- [ ] `workouts` / `workout_sets` / `routines` に `SoftDeletes` を導入
- [ ] `exercises` は**対象外**。`workout_sets.exercise_id` が RESTRICT で、
      論理削除だと「削除済みなのに参照が生きている」状態になり整合が壊れる
- [ ] `body_logs` は `unique(user_id, measured_on)` があるため、
      論理削除だと同日再登録ができなくなる。**対象外**とし、
      代わりに削除前の確認ダイアログで担保する
- [ ] 削除後に「元に戻す」導線を出す(直後のみ)
- [ ] **既存の集計・履歴クエリがすべて論理削除済みを除外することを確認**
      (Eloquent は自動で除外するが、`DB::table()` で書いたクエリは除外しない。
      `WorkoutSetRepository` は `DB::table` を使っている箇所があるので要確認)
- [ ] `DeleteUserService` は物理削除のまま(ユーザー削除は完全消去が正しい)

## 受入条件
- [ ] 終了済みワークアウトを編集モードで修正できる
- [ ] 修正しても `progression_snapshot` が変わらない(テストで検証)
- [ ] 過去の日付でワークアウトを作れる。未来日は弾く
- [ ] 過去日のワークアウトの目標が、その日付より前の記録から算出される(テストで検証)
- [ ] workouts / workout_sets / routines が論理削除になり、復元できる
- [ ] **論理削除したデータが集計・履歴・ナビ計算に含まれないことをテストで検証**
      (特に `DB::table()` で書かれたクエリ)
- [ ] 既存の220テストが通る
